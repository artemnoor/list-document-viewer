## Объём следующего стабильного MVP

**Вердикт пользователя: Сейчас перед изменением схемы.**

Ввести минимальные версионированные миграции до добавления новых полей/таблиц. Отдельный schema namespace и сложный deployment pipeline необязательны.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Что подтверждено

Gateway и standalone Extraction создают схемы на старте; у Linking уже есть собственный механизм миграций.

- [phystech-trace/gateway/main.py](../../phystech-trace/gateway/main.py) — ensure_database: CREATE TABLE IF NOT EXISTS.
- [phystech-trace/services/structured-extraction/runtime/server.mjs](../../phystech-trace/services/structured-extraction/runtime/server.mjs) — CREATE TABLE и индекс выполняются при запуске.
- [phystech-trace/services/document-linking/server/migrate.ts](../../phystech-trace/services/document-linking/server/migrate.ts) — Существующий migration entry point.

## Причина и границы вывода

IF NOT EXISTS не обновляет столбцы, индексы и семантику старых данных; несколько сервисов могут одновременно менять общую БД.

## Рекомендуемое решение

До первого изменения схемы добавить нумерованные SQL-миграции для Gateway/Extraction с таблицей применённых версий и одним мигратором под блокировкой. У Linking сохранить существующий runner. Можно использовать одну PostgreSQL БД без новых schema namespaces и отдельной deployment-платформы.

## Последовательность будущего изменения

1. Зафиксировать baseline существующих таблиц и проверить его на сохранённой БД, не помечать произвольную схему совместимой.
2. Добавлять поля project scope/run manifest/counter отдельными миграциями с безопасным backfill; порядок согласовать с существующими Linking migrations.
3. Запускать миграции одной явной командой/Compose one-shot step до старта новых readers; runtime проверяет версию. До опасных изменений проверять backup/restore.

## Проверка исправления

- Чистая БД и база текущего коммита обновляются до одной схемы без потери данных.
- Повторная команда безопасна, конкурентный мигратор блокируется; несовместимая версия даёт not ready.

## Критерий приёмки MVP

Минимальные версионированные миграции реально применяются до изменения схемы и проверены на старой базе. Enterprise migration pipeline и отдельные namespaces не требуются.

## Что отложено

Сложные online expand/contract deployments, несколько ролей DDL/runtime и независимые schema namespaces — по мере роста нагрузки/числа deployments.

Исходная расширенная проработка ниже сохранена как справочный вариант; она не расширяет текущий scope. При расхождении объёма приоритет имеют разделы MVP выше.

## Расширенный вариант для следующих этапов

Выбрать один deployment migration job с версионированным SQL-реестром и блокировкой мигратора. Таблицы могут оставаться в одной БД, но у каждой один владелец и отдельная история миграций/schema namespace. Не переписывать уже применённые миграции Linking.

## Расширенный вариант: возможные шаги

1. Сделать baseline существующей схемы: version/checksum и проверки фактических columns/constraints. Помечать baseline только после совпадения, не по наличию одной таблицы.
2. Добавить expand/backfill/validate/contract миграции для ownership, manifests и counter. Большие backfill выполнять порциями с возможностью продолжения.
3. На startup сервис проверяет совместимость schema version и не пишет DDL; миграции имеют отдельную роль, runtime — минимальные права.
4. Отработать backup/restore и forward fix. Destructive contract допускается после обновления всех readers; rollback кода не всегда означает обратимость данных.

## Расширенный вариант: будущие проверки

- Чистая БД, база на коммите 2e6da4b2 с сохранёнными данными, повторное применение и два одновременных мигратора.
- Прерывание backfill; несовместимая схема даёт not ready; восстановление резервной копии сохраняет evidence и project membership.

## Критерий полного закрытия исходного замечания

Развёртывание воспроизводимо обновляет старые и новые базы, все сервисы явно проверяют совместимость версии схемы.
