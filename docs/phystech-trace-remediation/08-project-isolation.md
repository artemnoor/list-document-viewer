## Объём следующего стабильного MVP

**Вердикт пользователя: Упростить.**

Project scope и изоляция запросов/кэша сейчас; отдельную полную подсистему blobs/artifacts внедрять постепенно.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Что подтверждено

Модель хранения подтверждает риск: глобальный parser document ID и extraction history без project scope.

- [phystech-trace/gateway/main.py](../../phystech-trace/gateway/main.py) — trace_documents содержит локальный id и parser_document_id; source_lookup проверяет проект, но пользовательских прав нет.
- [phystech-trace/services/structured-extraction/runtime/server.mjs](../../phystech-trace/services/structured-extraction/runtime/server.mjs) — trace_extractions и cache lookup ключуются document_id, input_hash, mode; project_id отсутствует.

## Причина и границы вывода

Идентичность одинаковых байтов смешана с экземпляром документа и историей обработки в конкретном проекте. Даже одинаковый файл может иметь разные роли, политику и экспертные исправления.

## Рекомендуемое решение

Сохранить текущие Parser/JSONB-хранилища. Использовать уже существующий trace_documents.id как экземпляр документа проекта и добавить его вместе с project_id в Extraction storage, history, cache и ограничения уникальности. Одинаковые байты могут оставаться дедуплицированными в Parser, но computed results и история не переиспользуются между проектами.

## Последовательность будущего изменения

1. Все lookup/latest/history/result запросы принимают project scope и проверяют принадлежность document instance. Parser document_id — только upstream locator.
2. Ключ cache и version counter включает project_document_id плюс fingerprint входа и настроек; убрать глобальный reuse по одному parser ID.
3. Мигрировать существующие записи по точному сопоставлению membership/hash; неоднозначные записи не раскрывать и не приписывать случайному проекту.

## Проверка исправления

- Одинаковый файл в двух проектах имеет раздельную видимую историю и не переносит решения/согласие.
- Чужой extraction_id и глобальный list/latest не раскрывают результат даже при известном parser ID.

## Критерий приёмки MVP

Все вычисленные результаты и запросы изолированы по проекту и экземпляру документа; отдельный blob registry или object storage не требуются.

## Что отложено

Отдельные blob/artifact сущности, общий безопасный кэш, RLS и управляемая межпроектная дедупликация — после измерения объёмов и появления соответствующих требований.

Исходная расширенная проработка ниже сохранена как справочный вариант; она не расширяет текущий scope. При расхождении объёма приоритет имеют разделы MVP выше.

## Расширенный вариант для следующих этапов

Разделить blob(source_hash), project_document(instance_id, project_id, blob_id, role) и immutable parser/extraction artifacts. Общий физический blob допустим; права и вычисленные результаты привязаны к экземпляру и доверенному scope.

## Расширенный вариант: возможные шаги

1. Все history/latest queries адресовать через project_document_id; upstream document_id оставить техническим идентификатором и не считать ACL.
2. Ключ повторного использования включает hash входа, версии engine/schema/model/prompt, настройки и допустимый policy scope. Для первого исправления запретить reuse Extraction между проектами.
3. Составные FK/constraints предотвращают связывание run с чужим документом; RLS можно добавить вторым рубежом, но она не заменяет сервисные права.
4. Мигрировать старые записи через membership и точный hash; неоднозначные записи карантинировать, не угадывать принадлежность.

## Расширенный вариант: будущие проверки

- Одинаковый файл загружен A и B: общие байты, разные видимые истории, роли, согласие и решения.
- Проверить все latest/history/source endpoints, прямые extraction_id и удаление одного проекта без потери общего blob другого.

## Критерий полного закрытия исходного замечания

Любой результат однозначно относится к проектному экземпляру; знание content hash или parser ID не раскрывает чужую историю.
