## Объём следующего стабильного MVP

**Вердикт пользователя: Упростить.**

Локальный MVP — один процесс Gateway, один исполнитель проекта и простая защита повторного запуска. Очередь с lease/fencing позже при горизонтальном масштабировании.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Что подтверждено

ACTIVE_TASKS локален процессу; гонка нескольких Gateway здесь не исполнялась.

- [phystech-trace/gateway/main.py](../../phystech-trace/gateway/main.py) — ACTIVE_TASKS, process, retry, lifespan и _resume_later.
- [phystech-trace/services/document-linking/server/worker.ts](../../phystech-trace/services/document-linking/server/worker.ts) — Linking уже использует BullMQ, claimJob и heartbeat; эту защиту нельзя приписывать всему Gateway.

## Причина и границы вывода

Запись status='running' и локальная проверка dict не предоставляют атомарное владение проектом. Несколько startup recovery могут одновременно возобновить работу.

## Рекомендуемое решение

Зафиксировать поддерживаемый локальный профиль: ровно один процесс Gateway/один Uvicorn worker, без replicas и автоматического горизонтального масштабирования. Сохранить ACTIVE_TASKS как локальный handle, но атомарно регистрировать active_run_id в PostgreSQL и проверять его вместе с input_revision при завершении. Для дополнительной защиты от случайного второго процесса допустима одна session advisory lock на отдельном соединении; полноценная очередь Gateway не нужна.

## Последовательность будущего изменения

1. Startup/Compose и документация явно запрещают несколько Gateway workers/replicas в MVP. Второй экземпляр должен fail fast при использовании guard lock, а не вести параллельный recovery.
2. Стартовать один run проекта через атомарный переход состояния и зарегистрированный run_id; повтор process/retry возвращает существующий run либо 409. Snapshot фиксируется в той же транзакции.
3. При рестарте единственного Gateway согласовать сохранённые stages и downstream idempotency keys. Результат публиковать условным UPDATE по active_run_id/revision; при потере guard/DB ownership остановить дальнейшие действия и завершение.

## Проверка исправления

- Два одновременных process/retry в поддерживаемом одном процессе дают один run.
- Рестарт Gateway безопасно восстанавливает run; повторный запуск конфигурации со вторым процессом обнаруживается/отклоняется. Поведение двух активно работающих replicas не объявляется поддержанным.

## Критерий приёмки MVP

В заявленном локальном single-process профиле нет двойного логического запуска, recovery проверен и результаты защищены run/revision checks. Горизонтальная отказоустойчивость остаётся открытым ограничением.

## Что отложено

Durable queue, lease/heartbeat и fencing нужны до разрешения нескольких экземпляров Gateway или внешних оркестраторов с перекрывающимися исполнителями. Run ID не выдаётся за полноценный fencing token.

Исходная расширенная проработка ниже сохранена как справочный вариант; она не расширяет текущий scope. При расхождении объёма приоритет имеют разделы MVP выше.

## Расширенный вариант для следующих этапов

Для существующей архитектуры начать с PostgreSQL run queue и lease, без второго обязательного брокера. Gateway создаёт run в БД; dispatcher атомарно захватывает задание, продлевает lease и передаёт fencing token при каждой записи. Linking остаётся на существующей BullMQ.

## Расширенный вариант: возможные шаги

1. Partial UNIQUE на один активный run проекта; транзакционный claim через SELECT FOR UPDATE SKIP LOCKED и UPDATE/RETURNING. Запись задания и manifest выполняется атомарно.
2. Использовать DB time для lease; каждое обновление состояния требует текущего token. Просроченный исполнитель теряет право публиковать результат.
3. Определить durable stage intents и idempotency keys до HTTP-вызова. ACTIVE_TASKS оставить локальным handle для cancellation.
4. Согласовать выключение/lease recovery. Advisory lock на отдельном соединении возможен как более простой вариант, но нельзя удерживать его через произвольный connection pool без владения session.

## Расширенный вариант: будущие проверки

- Два Gateway одновременно process/retry/recovery одного проекта: один логический run.
- Убить владельца после downstream вызова; новый worker продолжает тот же run; оживший старый worker не перезаписывает результат.

## Критерий полного закрытия исходного замечания

Единственность логического владельца обеспечена БД, stale workers отсекаются. Допускается повтор физического HTTP-запроса, но не дублирование логического результата.
