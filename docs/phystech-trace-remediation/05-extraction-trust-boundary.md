## Объём следующего стабильного MVP

**Вердикт пользователя: Сейчас.**

Доверенная серверная политика внешней LLM и защита прямого доступа обязательны. Подписанные разрешения не обязательны для локального MVP.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Parser входит в раннюю защиту отдельно

До модельного этапа закрыть не только Extraction, но и прямые Parser endpoints оригинальных байтов /source, /content, /analysis, /pages, списка и metadata, upload/retry/review/delete. Единый service-auth guard + private default port, все Gateway callers передают отдельный credential; Origin/loopback не заменяют auth. Подробная [матрица Parser](39-parser-access-boundary.md) и задача C04a в [едином плане](../../.ai-factory/PLAN.md). Для самого guard миграции не нужны; полная project-scoped storage следует позже и не блокирует работу на frozen разрешённых fixtures.

## Что подтверждено

Подтверждено runtime/server.mjs: нет auth, классификация и согласие читаются из тела запроса.

- [phystech-trace/services/structured-extraction/runtime/server.mjs](../../phystech-trace/services/structured-extraction/runtime/server.mjs) — POST /api/extractions; общие GET /api/extractions, /api/documents и история по document_id.
- [phystech-trace/gateway/main.py](../../phystech-trace/gateway/main.py) — auth_headers применяется к Linking; запрос Extraction сейчас не содержит доверенной идентичности проекта.

## Причина и границы вывода

Проверка synthetic + allow_external_llm проверяет лишь заявление вызывающего клиента. Без доверенного project scope история и результаты глобально доступны.

## Рекомендуемое решение

Закрыть прямой анонимный доступ к Extraction отдельным межсервисным секретом и внутренней сетью. Добавить project scope. Перед внешним вызовом сервис загружает актуальную политику проекта из доверенного серверного источника (существующая общая БД подходит); разрешение в теле запроса не может расширить её. Полноценные подписанные capabilities пока не нужны.

## Последовательность будущего изменения

1. Gateway аутентифицирует пользователя и проверяет owner/project scope; Extraction аутентифицирует Gateway отдельным сервисным секретом. Браузеру секрет не выдаётся.
2. По доверенному project_id проверить существование проекта, принадлежность входного document/run и текущие classification/allow_external_llm. Проверку делать перед фактической отправкой; не считать JSON-флаги источником разрешения.
3. Закрыть глобальные list/latest/history запросы: только project-scoped чтение; применить ту же доверенную policy к Linking. Убрать data ports из публичного production-профиля.

## Проверка исправления

- Прямой вызов без service credentials и с чужим project/document отклоняется.
- Подмена confidential на synthetic в теле и отзыв согласия перед отправкой дают ноль внешних вызовов.

## Критерий приёмки MVP

Ни один внешний вызов не разрешается только клиентским параметром; чтения и вычисления ограничены доверенным project scope.

## Что отложено

Короткоживущие подписанные разрешения, audience, отдельные service identities и mTLS — при разделении контуров/сервисов и росте числа исполнителей.

Исходная расширенная проработка ниже сохранена как справочный вариант; она не расширяет текущий scope. При расхождении объёма приоритет имеют разделы MVP выше.

## Расширенный вариант для следующих этапов

Внутренний сервис принимает только аутентифицированные запросы Gateway/worker. Пользовательская политика хранится сервером; короткоживущее подписанное разрешение связывает project_id, document instance, run_id, input hash, policy revision, allowed provider, audience и срок действия.

## Расширенный вариант: возможные шаги

1. Убрать наружную публикацию внутренних data endpoints в production; минимальный отдельный probe может остаться доступным оркестратору.
2. Валидировать сервисную идентичность и scope перед чтением payload и перед каждым внешним вызовом. Клиентские флаги не могут расширить разрешение; отзыв согласия проверяется при отправке.
3. Закрыть глобальные listing/history endpoints; фильтровать по project_document_id и проверять право на исходный extraction_id.
4. Аналогичную доверенную политику применить к Linking; общий service token без контекста проекта недостаточен.

## Расширенный вариант: будущие проверки

- Запрос без credentials, с неверной audience/истёкшим разрешением, чужим extraction_id и несовпадающим input hash отклоняется.
- Подменить confidential на synthetic в теле, повторить старое разрешение после отзыва согласия; mock provider должен зарегистрировать ноль отправок.

## Критерий полного закрытия исходного замечания

Пользователь не может обойти политику прямым запросом, а сервисная идентичность не предоставляет безусловный доступ к данным всех проектов.
