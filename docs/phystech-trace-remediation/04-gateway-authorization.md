## Объём следующего стабильного MVP

**Вердикт пользователя: Упростить.**

Локальная аутентификация и минимальные права сейчас; организационный IdP и расширенные роли позже.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Что подтверждено

Статически подтверждено отсутствие пользовательской проверки в маршрутах.

- [phystech-trace/gateway/main.py](../../phystech-trace/gateway/main.py) — ProjectCreate, list_projects, create_project, source_file, source_page, decide_link и process/retry не требуют user principal.
- [phystech-trace/docker-compose.yml](../../phystech-trace/docker-compose.yml) — Порты ограничены loopback; это ограничение сети, а не разграничение пользователей.

## Причина и границы вывода

project_id служит адресом объекта, но не доказательством права доступа. Таблица trace_projects не хранит владельца, список возвращает все проекты.

## Рекомендуемое решение

Для локального MVP достаточно одного явно настроенного пользователя и серверной сессии либо индивидуальных токенов, если интерфейс уже их поддерживает. Секрет не хранить в репозитории или Vue bundle. В Gateway одна общая проверка аутентификации для всех data routes. Проект хранит owner_id; если добавляется второй пользователь, доступ к каждому объекту уже ограничивается owner_id. Общая сервисная авторизация Extraction остаётся отдельной.

## Последовательность будущего изменения

1. Описать локальный профиль: localhost, один настроенный пользователь, без регистрации и организационного IdP. Отсутствие credentials не должно открывать данные.
2. Защитить список, проекты, upload/process/retry, source/page, history и review. Для cookie-сессии оставить HttpOnly/SameSite и защиту изменяющих запросов; запретить произвольный CORS.
3. Связать существующие проекты с явно настроенным локальным владельцем через миграцию. Закрыть обход через прямые service endpoints по №5.

## Проверка исправления

- Анонимные и неверные credentials не дают читать/менять данные, UI может войти и выйти.
- При наличии двух настроенных субъектов A не читает проект B; прямые source/history/review URL защищены.

## Критерий приёмки MVP

В локальном профиле все операции с данными требуют действительную аутентификацию; объектный owner scope проверяется. IdP и многоуровневая ролевая модель не являются условием закрытия MVP.

## Что отложено

Организационный OIDC/SSO, команды, приглашения и роли owner/editor/reviewer/viewer — при многопользовательском развёртывании.

Исходная расширенная проработка ниже сохранена как справочный вариант; она не расширяет текущий scope. При расхождении объёма приоритет имеют разделы MVP выше.

## Расширенный вариант для следующих этапов

Использовать существующий организационный OIDC-провайдер при наличии; конкретный провайдер ещё не выбран. Gateway проверяет сессию/токен и серверную membership: owner, editor, reviewer, viewer. Защита должна охватывать документы, страницы, историю, задания, бюджеты и экспертные решения.

## Расширенный вариант: возможные шаги

1. Спроектировать users/subjects и project_memberships; запретить доступ по умолчанию. Старые проекты оставить без публичного доступа до явного назначения владельца администратором.
2. Централизовать require_project_permission и фильтрацию SQL по субъекту. Проверять каждый ID в цепочке проекта и документа, а не только верхний project_id.
3. Определить безопасный flow Vue: при cookie-сессии HttpOnly/Secure/SameSite и CSRF-защита; ограничить CORS. Добавить журнал субъекта и действия без содержимого документов.
4. Закрыть обход через опубликованные Parser/Extraction/Linking API: внутренние сервисы доступны через Gateway и доверенную межсервисную идентичность.

## Расширенный вариант: будущие проверки

- Матрица ролей для каждого маршрута; анонимный/истёкший токен, подмена project/document/link/run ID.
- Пользователь A не видит проект B через список, скачивание, PDF page, историю, прямые URL и изменения решений.

## Критерий полного закрытия исходного замечания

Все операции используют идентичность и объектные права; миграция не назначает существующие проекты случайному первому пользователю.
