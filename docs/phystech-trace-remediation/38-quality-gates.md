## Gate Q0 до оптимизации

1. Назначить одного человека, который проверит исходные разрешённые документы, expected relations/rows/evidence и явные отрицательные пары, не опираясь на предсказания оцениваемой модели.
2. Зафиксировать размер/состав корпуса, hashes байтов/Parser/Extraction, единицы метрик, модель/prompt/settings, ресурсы и лимиты.
3. Q1 предварительно утверждён; запись согласования приведена выше, policy hash — ниже. До запусков отдельно согласовать тестовый execution/exposure. Любая новая числовая редакция требует нового утверждения.
4. Проверить измеритель и выполнить исходные повторные прогоны. Неисправленный scorer нельзя использовать как основание quality gate.
5. Сохранить результаты baseline со всеми FP/FN/ошибками/usage. Только после этого менять chunking/prompt/recovery/алгоритм.

Подготовка корпуса, исправление scorer и защита доступа не являются оптимизацией модели и могут предшествовать Q0. При нехватке бюджета/валидных labels baseline отмечается незавершённым; переход к оптимизации по этому плану остановлен. Изменение порогов после просмотра результата не считается прохождением gate: требуется новая policy version и повтор измерений.

## Утверждённый предварительный объём эталона

- **6 комплектов**, проверенных одним человеком: compact PDF/XLSX/DOCX; исходный широкий набор из 5 документов; два договора с повторяющимися суммами; явная отрицательная пара; неоднозначная пара; межчанковые таблицы с отсутствующим документом.
- Не менее **20 положительных отношений**, **30 соответствий строк**, **10 явно отрицательных пар**, **5 неоднозначных пар** во всём корпусе. Пары могут входить в разные комплекты; repeated appearances считаются отдельно в manifest.
- **5 независимых повторов на комплект**: 30 исходных run и столько же для кандидата. Resume/replay одного run не считается независимым повтором.
- Первый этап использует проверенные Extraction snapshots для отдельного Linking benchmark. Отдельный extraction/E2E срез включает PDF, XLSX, DOCX и хотя бы одну сложную/смешанную таблицу в каждом релевантном формате.
- Нельзя исключить широкий неуспешный комплект, negative/ambiguous cases или последний большой чанк ради прохождения.
- Разделить 4 dev-комплекта и 2 закрытых проверочных комплекта по шаблонам/операциям. Если один разметчик совмещает роли, это ограниченный вручную проверенный MVP gold, а не независимое двухэкспертное исследование. Проверочные исходы не использовать для настройки; при раскрытии обновить holdout.
- Если человек не может подтвердить предложенное количество labels, состав корректируется и согласуется **до** фиксации baseline; пустые pending packets не становятся отрицательными примерами.

Два независимых эксперта и арбитр не обязательны для ближайшего MVP. Их добавляют при расширении корпуса и перед более ответственным предметным пилотом.

## Утверждённые предварительные критерии приёмки

Метрики считаются для каждого из 5 повторов по всему корпусу; каждый повтор обязан пройти порог. Отдельно публикуются значения на каждом комплекте и worst case. Все дроби сопровождаются абсолютными TP/FP/FN/denominator; малый корпус не даёт основания заявлять промышленную точность.

| Измерение | Контракт Q1 | Что считается ошибкой |
| --- | --- | --- |
| Document/link precision | ≥ 0.95 в каждом повторе | Лишняя связь на явно размеченном основании |
| Document/link recall | ≥ 0.90 в каждом повторе | Пропущенное подтверждённое отношение |
| Link F1 | ≥ 0.92 в каждом повторе | Вычисляется из P/R без округления до сравнения |
| Row precision и recall | Каждая ≥ 0.90 | Неверное либо пропущенное соответствие строк |
| Направление принятых TP-связей | 100% | Перестановка source/target не засчитывается как TP |
| Разрешимость принятого evidence и совпадение raw_value | 100% | Неверный path/artifact/version/value; дефектный кандидат должен быть отклонён |
| Полнота обязательного supporting evidence | 100% на обязательных gold references для найденных TP | Подмена доказательства другой связью или отсутствие обязательной стороны |
| Явно отрицательные пары и критические противоречия | 0 ошибочно принятых связей | Ambiguous оценивается отдельно, не считается обычным negative |
| Неоднозначные пары | 100% остаются review/undetermined без автоматического human_confirmed | Неопределённость нельзя скрыть уверенным автоматическим решением |
| Processing coverage | 100% ожидаемых документов/строк имеют состояние | «Не обработано» нельзя назвать «связь не найдена» |
| Hard failure в пределах тестовых лимитов | 0 из 30 run после разрешённых bounded retries | Failed/timeout/budget-exceeded остаются неуспехом, даже если JSON результата валиден |
| Стабильность непустых gold-графов | Mean pairwise Jaccard ≥ 0.90, минимум пары ≥ 0.80 | Считается по каноническим документным отношениям; row stability публикуется отдельно |
| LLM Extraction: точность принятых размеченных значений/provenance | 100% | Точная типизированная нормализация по утверждённым правилам; выдуманный raw source недопустим |
| LLM Extraction: recall обязательных критичных полей | 100% | Список критичных полей фиксирует человек до baseline |
| LLM Extraction: recall остальных размеченных полей и строк | Каждая ≥ 0.95 | LLM-required прогон с fallback rules_only считается неуспешным |
| Cross-project/access/policy нарушения | 0 | Утечка source/analysis/history или внешняя передача без доверенного разрешения |
| Stale current publication / active-upload mutation | 0 | При несовпадении run/revision публикация отклоняется |

Пропущенные связи учитываются в recall; отсутствие найденного evidence не освобождает от FN. Неопределённые gold labels не входят в обычные P/R denominators; раскрытые моделью уверенные решения на них отдельно проваливают ambiguity gate. Пустой корректный negative граф имеет отдельный успех без искусственного precision=1; N/A не превращать в 0 или 100%. Статистику стабильности пустых отрицательных графов публиковать отдельно от положительных.

Равенство направления проверяется одновременно с отношением, поэтому часть direction ошибок уже входит в FP/FN. Эта дополнительная строка запрещает скрыть их в усреднённой accuracy.

## Утверждённые предварительные тестовые лимиты

Это границы приёмочного MVP-профиля, не универсальная производительность системы. При превышении до/во время обработки должен быть явный limited/failed, а не completed с потерей данных.

| Параметр | Контракт Q1 |
| --- | --- |
| Документы | До 10 уникальных файлов на комплект |
| Один исходный файл | Не более существующего лимита 25 MiB |
| PDF/изображения | До 100 страниц/растровых страниц в сумме на комплект |
| Табличные строки | До 2000 source rows в сумме; без произвольного раскрытия sparse used range |
| Нормализованный Extraction input | До 8 MiB UTF-8 JSON на Linking run; служебные payload bytes измерять отдельно |
| Один LLM request | До 16000 input tokens вместе с system prompt/schema и до 4000 output tokens |
| LLM-вызовы | До 40 суммарно на run для Extraction+Linking, включая ошибки, retries и repairs |
| Суммарные токены run | До 500000 input и до 100000 output; брать наиболее строгий из total/per-call/call-count лимитов |
| Время | До 120 секунд на один provider request и 20 минут на run |
| Исполнение | 1 Gateway process, 1 активный проект, 1 in-flight provider request |
| Повторы повреждённой части | Не более 2 дополнительных repair attempts; входят в общие calls/tokens/time |
| Исходный baseline | 6 × 5 run; общий тестовый exposure limit согласуется перед live, но не считается денежным ledger |

Лимиты токенов требуют preflight и учёта максимального output до отправки. Если provider не возвращает usage, использовать консервативный резерв/оценку в счётчиках и показывать unknown. Денежный потолок без достоверного тарифа не обещается. 30 × 40 вызовов — верхняя граница до 1200 запросов на один полный набор повторов, а не рекомендуемый расход; фактическое разрешение live и меньший exposure cap фиксируются отдельно до запуска.

## Baseline: что нужно заполнить

| Показатель | Baseline | Кандидат | Статус сейчас |
| --- | --- | --- | --- |
| P/R/F1, row P/R, direction, evidence | Не измерено | Не измерено | Ожидает frozen gold и исправления scorer |
| Per-repeat и per-scenario FP/FN | Не измерено | Не измерено | Не заменять данными compact smoke |
| Jaccard / hard failures / usage/time | Не измерено | Не измерено | Старый отчёт 0–2 не является новым baseline |
| Extraction critical/noncritical recall | Не измерено | Не измерено | Rules-only не засчитывается |
| Человек, версия labels, hashes/config | Не назначено / не заполнено | То же frozen основание | Требует фиксации |

Пройти абсолютные gates недостаточно для утверждения «стало точнее»: сравнить кандидата с baseline на том же frozen corpus, раскрыть изменившиеся FP/FN и все ухудшения. Если метрики не выросли, честно писать об улучшении исполнимости/лимитов или восстановлении, а не точности. Расширение корпуса/второй разметчик создают новую версию и новый цикл оценки.

## Статус согласования и оставшиеся gates

Q1 предварительно утверждён ответом пользователя. Это закрывает только согласование числового контракта. Конкретный человек, список критичных полей, frozen labels/hashes, исправленный scorer и измеренный baseline пока отсутствуют. Запуск любых application/model tests и фактический live exposure требуют отдельного согласования; число допустимых запросов в Q1 не является таким разрешением. Изменение утверждённых чисел/корпусного профиля — отдельная редакция с повторным согласованием.
