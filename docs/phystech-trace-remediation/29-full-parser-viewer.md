## Объём следующего стабильного MVP

**Вердикт пользователя: Позже; полный доступ сейчас.**

Сейчас дать доступ ко всему сохранённому Parser JSON. Полнотекстовый поиск, виртуализация и развитый UI позже.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Причина и границы вывода

Простое снятие slice для большого вложенного JSON может заморозить браузер. Части visual_layout и parts также могут отражать разные представления.

## Рекомендуемое решение

Сначала обеспечить авторизованный доступ ко всему уже сохранённому Parser JSON — раскрытие/скачивание полного результата и явная пометка краткого preview. Лимит 32 допустим только для превью, если остальные данные доступны обычным действием.

## Последовательность будущего изменения

1. Использовать существующий project-scoped result endpoint с проверкой прав и версии; не строить новый индекс/хранилище.
2. Дать действие «Полный JSON» или скачивание, включающее вложенные parts/tables и provenance без обрезки.
3. Явно обозначить число отображённых/всех элементов. Большой JSON можно отдавать файлом, не рендерить целиком в DOM.

## Проверка исправления

- В документе с 33+ parts последний и все вложенные элементы присутствуют в полном JSON.
- Доступ защищён owner/project scope, указан snapshot/version; preview не заявлен полным просмотром.

## Критерий приёмки MVP

Все сохранённые данные доступны, тихой обрезки нет. Расширенный исследовательский UI остаётся отложенным.

## Что отложено

Полный поиск, дерево структуры, server pagination, виртуализация таблиц и оптимизация DOM — после backend-стабилизации.

Исходная расширенная проработка ниже сохранена как справочный вариант; она не расширяет текущий scope. При расхождении объёма приоритет имеют разделы MVP выше.

## Расширенный вариант для следующих этапов

Пагинация/виртуализация, поиск и отдельные режимы: текст/страницы, таблицы/листы, дерево структуры и raw JSON. Canonical result выбирается явным правилом, raw/visual структуры не склеиваются с дублями.

## Расширенный вариант: возможные шаги

1. Сохранить точные locators в view model, показывать total/loaded/filtered counts, кнопки перехода к странице/таблице/совпадению.
2. Для умеренного JSON допустим клиентский индекс; для крупных artifacts — серверные paged endpoints по immutable artifact_id и cursor. Не скачивать весь проект заново на каждый клик.
3. Вложенные части обходить рекурсивно; таблицы раскрывать отдельно, merged cells и provenance не терять. Search scope явно обозначать.
4. Лимитировать объём одного рендера, но обеспечить доступ ко всем данным; сохранять selection при навигации и сбрасывать её при смене версии.

## Расширенный вариант: будущие проверки

- Документ с 33, 1000 и более частей, вложенными таблицами, совпадением в последнем элементе и пустыми частями.
- Переход по evidence открывает точный фрагмент за пределами первой страницы; измерить responsive UI/память на установленном максимуме.

## Критерий полного закрытия исходного замечания

Каждый part и таблица доступны через навигацию или поиск; нет тихого ограничения 32. Производительность проверена на максимуме поддерживаемого корпуса.
