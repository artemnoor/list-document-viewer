## Объём следующего стабильного MVP

**Вердикт пользователя: Позже.**

Сначала измерить объём и рост данных; пока сохранить существующее хранение и доказательства, не строить GC/архив заранее.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Причина и границы вывода

Нет единого владельца артефакта и жизненного цикла производных данных. Часть копий оправдана устойчивым snapshot, поэтому удалять их только по внешнему сходству нельзя.

## Рекомендуемое решение

Сохранить существующее хранение и начать с измерений: размер originals, Parser/Extraction JSON, Linking/checkpoints и темп роста на репрезентативных run. Не переносить артефакты и не вводить автоматическую очистку до оценки необходимости.

## Последовательность будущего изменения

1. Получить инвентаризацию размеров и доли дублирования без копирования приватного содержимого в общий отчёт.
2. Зафиксировать, какие копии нужны для immutable snapshot/evidence и recovery; определить текущие ограничения диска.
3. По результатам измерений отдельно принять решение о retention, архиве, object storage и безопасном GC.

## Проверка исправления

- Сравнить объём нескольких representative run и повторных обработок, проверить доступность исторического evidence.
- Убедиться, что измерение не модифицирует/не удаляет артефакты и не раскрывает чужие данные.

## Критерий приёмки MVP

Для локального MVP достаточно отчёта об объёме/росте и сохранности evidence. Исходная задача retention/GC остаётся открытой и отложенной.

## Что отложено

Полная стратегия canonical artifacts, архивирование, retention/holds, content-addressed storage и mark-and-sweep GC — после измерений.

Исходная расширенная проработка ниже сохранена как справочный вариант; она не расширяет текущий scope. При расхождении объёма приоритет имеют разделы MVP выше.

## Расширенный вариант для следующих этапов

Оригинал и крупный immutable JSON — в артефактном хранилище по hash; PostgreSQL хранит metadata, ACL, зависимости и компактные индексы. Снимок Linking может ссылаться на immutable upstream, если гарантированы доступность и срок хранения.

## Расширенный вариант: возможные шаги

1. Измерить размеры/количество копий на синтетическом и разрешённом корпусе. Назначить canonical owner для original, Parser, Extraction, checkpoints, decisions и diagnostics.
2. Определить retention по классу данных и проекту, архивирование, legal hold/удержание аудита, сроки backups. Численные сроки требуют решения владельца данных.
3. GC выполняет mark-and-sweep с grace period и повторной проверкой ссылок; active run/историческое решение блокируют удаление нужного evidence.
4. Мигрировать dual-read с проверкой hash; лишь затем убрать необязательные JSON-копии. Удаление проекта отзывает доступ сразу, физическая очистка учитывает общие blobs и резервные копии.

## Расширенный вариант: будущие проверки

- Удаление одного из двух проектов с одинаковым blob не ломает другой; historical evidence разрешается после архивации.
- GC одновременно с upload/run commit, interrupted GC, restore из backup, неверный hash артефакта.

## Критерий полного закрытия исходного замечания

Есть измеренная экономия, документированная retention policy и проверяемая очистка без потери доказательств и межпроектных утечек.
