## Объём следующего стабильного MVP

**Вердикт пользователя: Сейчас.**

Ready не доказывает качество. Нужны policy допуска и явные ограничения для частичных/непроверенных данных.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Причина и границы вывода

Транспортная готовность результата подменяет качество его содержимого. Warning не всегда критичен, а отсутствие warning не подтверждает все значения.

## Рекомендуемое решение

Добавить версионированную policy допуска с исходами accepted, accepted_with_limits, review_required, blocked. Сопоставить фактические поля разных parser adapters: processing_status, quality, warnings, stale и статусы source values. Не изобретать универсальный OCR confidence threshold без калибровки.

## Последовательность будущего изменения

1. Составить таблицу реальных Parser-полей и статусов по fixtures/коду. Неизвестное критичное состояние трактовать как требующее проверки.
2. Блокировать stale/неполный критичный источник; некритичные предупреждения допускать с машинно читаемыми ограничениями. Сохранять исключённые страницы/ячейки и причины.
3. Проверять evidence каждого утверждения: неразрешённое OCR-значение не становится доверенным после LLM. Экспертное исправление создаёт новую версию и инвалидирует downstream.
4. Разделить технический completed и предметную пригодность комплекта; правила отражаются в API и документации.

## Проверка исправления

- Матрица ready + partial/failed/unknown quality, stale, пустые parts, предупреждения разных уровней.
- Таблица с неверной OCR-цифрой, пропущенной страницей и неподтверждённой суммой не получает неограниченный итог; безопасное предупреждение не блокирует весь комплект.

## Критерий закрытия

Для каждого документа есть явное решение допуска и ограничения. Полный результат не скрывает непроверенные критичные данные.
