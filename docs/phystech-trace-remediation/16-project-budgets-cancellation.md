## Объём следующего стабильного MVP

**Вердикт пользователя: Упростить.**

Сохраняемые лимиты вызовов, времени и токенов плюс остановка дальнейших вызовов сейчас; полный финансовый ledger позже.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Что подтверждено

Linking учитывает вызовы/usage; общей транзакционной квоты Gateway нет.

- [phystech-trace/services/document-linking/src/linking/llm-matcher.ts](../../phystech-trace/services/document-linking/src/linking/llm-matcher.ts) — calls, input/output tokens, costAmount, maxRunMs и maxInputTokens.
- [phystech-trace/gateway/main.py](../../phystech-trace/gateway/main.py) — ProjectCreate и process не задают общий денежный/токенный бюджет и endpoint отмены.
- [phystech-trace/services/document-linking/evaluation/README.md](../../phystech-trace/services/document-linking/evaluation/README.md) — Pilot ledger уже различает резерв и неизвестную стоимость; это не production budget.

## Причина и границы вывода

Локальные ограничения worker не объединяют Extraction, Linking, retries и конкурентные запуски проекта. Пропавшая usage не означает бесплатный вызов.

## Рекомендуемое решение

Ввести сохраняемые лимиты на run для числа вызовов, суммарных input/output tokens и времени, объединяя Extraction, Linking и все retries. Ограничивать максимальный output одного вызова. Базовая отмена ставит cancel_requested и предотвращает следующие вызовы; удалённый уже отправленный запрос может завершиться и учитывается отдельно.

## Последовательность будущего изменения

1. Preflight проверяет размер/оценку входа, max_calls, max_tokens и deadline. Перед вызовом сверять остаток и допустимый максимум output; без достоверного token count использовать консервативную оценку и явно отмечать её.
2. Сохранять counters до/после каждого вызова и восстанавливать их после рестарта. Retry и повтор Linking не сбрасывают использованный run budget; новый run создаётся явно.
3. Проверять отмену до постановки задачи, между чанками и перед current publication. Передавать AbortSignal, где транспорт поддерживает; UI показывает calls/tokens/time и unknown usage.

## Проверка исправления

- Каждый лимит прерывает дальнейшие запросы, включая retries обоих LLM-этапов; рестарт не обнуляет counters.
- Отмена до и во время вызова не допускает следующего; поздний ответ не возобновляет отменённый run.

## Критерий приёмки MVP

Система ограничивает вызовы, время и токены в рамках объявленной точности учёта и позволяет остановить дальнейшую работу. Денежный потолок не обещается без финансового ledger/достоверных тарифов.

## Что отложено

Денежные reservations/settlement, валюты/версии тарифов, project-wide billing и финансовый ledger — при реальной потребности в управлении расходами.

Исходная расширенная проработка ниже сохранена как справочный вариант; она не расширяет текущий scope. При расхождении объёма приоритет имеют разделы MVP выше.

## Расширенный вариант для следующих этапов

Серверный budget ledger: limit, reserved, actual, unknown. До каждого вызова атомарно резервировать верхнюю оценку по версии тарифа/максимальному output, затем сверять usage. Лимиты проекта и конкретного run учитываются совместно.

## Расширенный вариант: возможные шаги

1. Добавить max_cost/currency, input/output tokens, calls, wall-clock deadline, concurrency. Тариф хранить с timestamp и источником; конкретные текущие цены в этом исследовании не утверждаются.
2. При отсутствии usage сохранять резерв до reconciliation, показывать unknown; повтор не обнуляет потраченный бюджет.
3. Отмена создаёт durable cancel_requested; Gateway и worker проверяют её перед вызовом/публикацией, AbortSignal отменяет локальное ожидание при возможности.
4. UI показывает прогноз, подтверждённый расход, резерв, неизвестную часть и причину остановки. Late response остаётся в аудите, не возобновляет отменённый run.

## Расширенный вариант: будущие проверки

- Параллельные requests на остаток бюджета; retry не выходит за лимит; стоимость отсутствует/приходит поздно.
- Отмена до очереди, во время модели и перед commit; новые вызовы не стартуют, уже принятые провайдером учитываются.

## Критерий полного закрытия исходного замечания

Нет вызова без reservation; превышение лимита даёт явный budget_exceeded. Пользователь может остановить дальнейшую обработку и видит фактические ограничения отмены.
