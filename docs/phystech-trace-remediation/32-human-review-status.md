## Причина и границы вывода

Технический статус отношения используется как признак человеческой проверенности. Экспертное решение хранится слишком близко к заменяемому результату вычисления.

## Рекомендуемое решение

Разделить машинное предложение/техническую валидацию, человеческую verification и актуальность источников. Любая автоматическая связь с not_reviewed доступна уполномоченному reviewer; алгоритмический confirmed не означает human_confirmed.

## Последовательность будущего изменения

1. Определить матрицу допустимых переходов и поясняющие подписи. Ошибочную evidence связь нельзя сделать достоверной одной кнопкой: сначала исправление источника/основания с аудитом.
2. Решения хранить append-only: actor, timestamp, rationale, run_id, link/evidence fingerprint и ожидаемая revision. Проверять optimistic concurrency/ETag.
3. Исправить UI кнопок, счётчиков pending и списков фильтрации одновременно; Gateway и Linking проверяют те же права/переходы.
4. После перерасчёта решение остаётся у исторической связи. Автоперенос допустим лишь по строгому совпадению основания и отдельной политике, иначе новый review.

## Проверка исправления

- Все комбинации machine status × verification_status; confirmed + not_reviewed имеет кнопки и входит в pending.
- Два reviewers конфликтуют, viewer нажимает прямой PATCH, старое решение применяется к новому run — запросы корректно отклоняются.

## Критерий закрытия

Техническое принятие и решение специалиста различимы в API/UI. Каждое автоматическое предложение можно проверить без потери истории.
