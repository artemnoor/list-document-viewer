## Объём следующего стабильного MVP

**Вердикт пользователя: Сейчас перед публикацией.**

Сохранить отдельный локальный профиль. Production secrets и validation обязательны до выхода за изолированный localhost; публикация не входит в текущую работу.

Объём ниже уточнён по пользовательской оценке всех 35 планов. Расширенные решения не являются обязательствами MVP; отложенное замечание не считается устранённым. Исследование остаётся без реализации.

## Что подтверждено

Значения по умолчанию и NODE_ENV=development подтверждены Compose; компрометация секретов не установлена.

- [phystech-trace/docker-compose.yml](../../phystech-trace/docker-compose.yml) — POSTGRES_PASSWORD и API_BEARER_TOKEN имеют известные fallback; Linking API/worker используют development.
- [phystech-trace/services/document-linking/server/config.ts](../../phystech-trace/services/document-linking/server/config.ts) — Существующие правила конфигурации нужно сохранить и проверить в production.
- [phystech-trace/services/document-linking/server/config-check.ts](../../phystech-trace/services/document-linking/server/config-check.ts) — Имеется отдельная проверка конфигурации.

## Причина и границы вывода

Удобный локальный bootstrap может стать фактической production-конфигурацией. Локальные defaults не должны проходить production startup validation.

## Рекомендуемое решение

Для локальной разработки сохранить отдельный профиль, привязанный к localhost, с явно обозначенными dev defaults. До публикации добавить production профиль: обязательные уникальные env/file secrets, NODE_ENV=production, validation и закрытые внутренние порты. Отдельный secret manager не обязателен для MVP.

## Последовательность будущего изменения

1. Не смешивать dev и production defaults; production с пустым/известным placeholder секретом не стартует.
2. Согласовать существующий config-check Linking с API/worker и Gateway. Настроить уникальные service credentials без включения значений в Git/логи.
3. При смене пароля существующей БД обновлять роль, а не только POSTGRES_PASSWORD; подготовить ручную документированную ротацию.

## Проверка исправления

- Локальный профиль запускается в изолированном режиме; production defaults/пустые secrets отклоняются.
- Production-проверки выполняются до любой публикации, включая реальные внутренние ports/auth.

## Критерий приёмки MVP

Локальный профиль явно ограничен; production validation и уникальные секреты обязательны перед публикацией. Текущий локальный этап не требует secret manager и автоматизированной ротации.

## Что отложено

Secret manager, автоматическая ротация/выдача краткоживущих credentials и развитое управление сервисными identities — при публичной/организационной эксплуатации.

Исходная расширенная проработка ниже сохранена как справочный вариант; она не расширяет текущий scope. При расхождении объёма приоритет имеют разделы MVP выше.

## Расширенный вариант для следующих этапов

Разделить dev и production конфигурации. Production требует уникальные секреты через secret manager/файлы secrets, NODE_ENV=production, доверенную auth policy и закрытые внутренние порты. Не хранить реальные значения в примерах или итоговых отчётах.

## Расширенный вариант: возможные шаги

1. Определить обязательные переменные и запрет известных placeholder/default значений, пустых токенов и небезопасных сочетаний; проверить API и worker одинаково.
2. Согласовать требования существующего Linking config-check, URL/TLS, CORS и reverse proxy с production Compose.
3. Ротацию БД выполнять через изменение пароля роли, а не только POSTGRES_PASSWORD: существующий volume сохраняет старую учётную запись.
4. Service credentials разделить по назначению/аудитории; предусмотреть краткое окно ротации и отзыв старого ключа. Удалить секреты из diagnostics/logs.

## Расширенный вариант: будущие проверки

- Production не запускается с placeholder, отсутствующим секретом или development; dev запускается по документированному сценарию.
- Ротация на существующем volume; старый токен отклоняется, действующие задачи получают контролируемый retry/завершение.

## Критерий полного закрытия исходного замечания

Production профиль проходит validation и negative tests, реальные секреты выдаются доверенным способом. Публикация deployment не выполняется в этом исследовании.
