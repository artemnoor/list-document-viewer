## Изменения

### Linking

- Полный небольшой контекст остаётся одношаговым. Для больших комплектов применяется последовательность bounded discovery → semantic routing по всем парам документов → проверка выбранных оригиналов. Навигация сводит контекст, но не принимается как evidence; подробный финальный reduce по всему комплекту не выполняется. Поиск кандидатов не использует жёсткий фильтр по номерам, суммам или типам.
- Все скаляры, индексируемые evidence registry, передаются модели. Текст длинных значений разделяется на точные срезы с offset. Повторяющиеся координатные поля provenance не размножаются в ограниченных запросах: оригинальные координаты остаются в источнике и разрешаются кодом. `source_text` сохраняется для смыслового чтения.
- `reference_id` и `row_id` присоединяет код до упаковки запроса. Их доступность больше не зависит от полноты пересказа модели. Каждый запрос проверяется по фактическому сериализованному размеру.
- Manifest сообщает модели существующие документы и число их фрагментов. Можно запросить дополнительные оригиналы, в том числе для разрешения неоднозначности; расширение также ограничено бюджетом.
- В checkpoint сохраняются план, hash источников/инструкции/настроек, ответы, выполненные задачи, coverage, невалидные JSON, usage и попытки исправления evidence. При продолжении выполненные запросы не повторяются. Исправление evidence соблюдает лимит вызовов одной worker-итерации.
- Невалидный JSON/структура ограниченной задачи получает не более двух первоначальных попыток. Исчерпанные попытки не сбрасываются при resume. Нехватка минимального бюджета всех задач выявляется до первого вызова; незавершённый граф не становится полным.
- Исправлен дефект: неверный row ID удалялся, но связь могла остаться `confirmed`. Теперь она становится `review`, а row-ошибки допускаются к исправлению моделью.
- Оригинальные значения, принадлежность reference документу, JSON-пути и provenance проверяются прежними механизмами. Нет поиска «похожего» значения взамен неверной ссылки модели.
- Объединение в коде убирает только идентичные предложения с теми же типом, направлением, строками и парами evidence-путей. Разные строки и альтернативные договоры сохраняются; расхождение статусов переводит дубликат в `review`.
- В существующем расширяемом `processing_metadata.analysis_coverage` сохранены состояния `linked`, `no_link_found`, `insufficient_evidence`, `not_processed` и счётчики задач/ссылок. Невалидная evidence не превращается в отрицательное заключение. `rejected` не считается найденной связью.

### LLM-assisted Extraction

- Убраны выбор первых восьми/последней строки, лимит 180 элементов и усечение текста. Контекст содержит полный доступный inventory Parser; запросы упаковываются до 33000 символов, оставляя место для repair.
- Табличные заголовки повторяются вместе с рядами; длинные исходные элементы передаются точными срезами с перекрытием. Модель видит определения всех полей, а не только полей предварительного rules-классификатора.
- Заголовки адресуются реальными доступными Parser source IDs вместо выбора синтетического ID при наличии исходных IDs. Проверяются существование ID, видимость в текущем фрагменте и точная подстрока в оригинальном Parser JSON. Координаты модель не задаёт.
- Ошибки JSON/schema/grounding получают ограниченное локальное исправление. Отклонённые кандидаты диагностируются. Ошибка LLM остаётся ошибкой, автоматического `rules_only` fallback нет.
- Различающиеся классификации и mappings требуют review. Несколько разных grounded-значений одного поля сохраняются как конфликт с альтернативами, без произвольного выбора первого.
- Результаты фрагментов, исходные ответы всех попыток, конфликты и отклонения доходят до существующего `extraction_engine.llm.usage.quality_analysis`. Предусмотрен callback `POLZA_ON_PROGRESS`; ошибки содержат завершённые и необработанные фрагменты.
- Учёт попыток/usage отделён от выбора исправленного результата. Учитываются ответы до repair; неполные данные о расходе остаются неизвестными, известная часть записывается отдельно. Duration измеряет полную операцию.

Версии контрактов `1.0.0`/`1.2.0`, Swagger, endpoints и финансовые правила не менялись. Новая диагностика помещена в уже расширяемые metadata/usage. Общий план 35 исправлений и его checklist не изменялись.

### Routing false-negative control (13.11.2026)

Проверен отдельный риск: маршрутизатор мог объявить `no_relation` по кратким summary и тем самым исключить пару до проверки оригиналов. Теперь routing-негатив предварительный: он обязан сослаться на проверяемые оригинальные anchors с обеих сторон и покрыть ими каждый исходный фрагмент пары. Затем каждая такая пара проходит verification по выбранным оригинальным значениям и строкам. Большой аудит разбивается на ограниченные пары source-фрагментов; если даже такая задача не помещается в Q1, обработка завершается явной ошибкой с сохранённым routing checkpoint, а пара не получает `no_link_found`. Для вывода `no_link_found` все audit-подзадачи пары должны вернуть явное подтверждение после проверки.

Добавлены независимые hand-authored synthetic labels: шесть направленных положительных отношений и четыре отрицательных пары, покрывающие все десять возможных пар документов; набор содержит два договора и два счёта с повторяющимися суммами, один реестр двух операций и два соответствия строк. Метки зафиксированы в `phystech-trace/services/document-linking/evaluation/synthetic-routing-gold.json` до mock-предсказаний. Это известная synthetic-разметка, не экспертный gold для реальных документов.

На намеренно состряпанном adverse mock routing отправил все пары как `no_relation`: Recall routing = **0/6**, verification восстановил **6/6**; итоговые Precision/Recall/F1 = **1/1/1**, направление и обе строки совпали, evidence diagnostics = **0**, покрытие источников = **364/364**. Использовано 12 Linking вызовов плюс 12 зарезервированных Extraction = **24/40 Q1**, длительность локального прогона 56–161 ms в повторах. Ответы verification в этом тесте сценарно возвращают заранее написанные labels; поэтому метрики показывают корректность механизма восстановления, а не качество модели/семантики. Токен usage провайдера и реальная стабильность не измерялись.

На том же committed full-five native Parser fixture отдельный негативный mock теперь реально проходит аудит всех **10/10** пар: **27** вызовов Linking + **12** Extraction reserve = **39/40 Q1**, максимум оценки входа **15,600/16,000 tokens**, ссылки обработки **13,261/13,261**. Это на 13 вызовов больше прежнего candidate-only structural mock с 14 Linking вызовами (26/40 вместе с reserve): сравнение подтверждает стоимость проверки ложных отрицаний, а не семантический Recall. Запас Q1 — один вызов; дополнительные repair/context request исчерпают согласованный предел и должны остаться незавершённой обработкой с checkpoint. Порог Q1 не менялся.

Тест также делает oversized audit явным: оригинальный fragment, который не помещается даже в bounded verification, сохраняет routing checkpoint и не становится отрицательным результатом. Текущее покрытие гарантирует проверку моделью выбранных anchors каждого фрагмента и всех значений выбранных строк; оно не гарантирует, что каждый невыбранный факт длинного фрагмента был повторно перечитан в adverse audit. Это остаётся главным риском recall и требует живого прогона/экспертного gold.

Проверки этой итерации: `npm run typecheck` без ошибок; полный Linking suite — **82 passed, 5 skipped, 0 failed из 87**; targeted Extraction/Parser/C03b suite — **50/50 passed**. Внешняя сеть и live Polza не использовались.

В C02 и C03b найдены ошибки подготовки двух существующих тестов: они ожидали проверки hash/schema, но оставляли вход, отвергаемый более ранней проверкой pending/identity. Исправлены только fixtures, чтобы действительно достигать проверяемого gate. Компиляторы разметки, scorers и пороги C02–C03b не изменены. Неуспешные промежуточные запуски также сохранены.

## Следующий измерительный этап

Независимый завершённый gold не найден. В evaluation лежат pending packets и unadjudicated scenarios, а README прямо сообщает об отсутствии reviewed gold/baseline. Автоматическая генерация «экспертных» labels не выполнялась.

1. Человек вслепую завершает packets C02: направление, тип отношений, строки, парное evidence, явные negatives/ambiguity и отсутствующие документы. Использовать существующие `eval:prepare-annotations` и `eval:compile-annotations -- --mode single`; labels должны предшествовать predictions. Для Extraction заполнить существующий gold C03b по Parser JSON и исходным значениям.
2. Заморозить одинаковые hashes документов и gold, версию Parser/Extraction, prompt/model, бюджеты, критичные поля и режим `llm_assisted`. Сценарии C02 уже включают несколько договоров, совпадающие суммы, неоднозначность и отрицательные пары; локально дополнены средние строки и PDF/XLSX/DOCX inventory. Эксперт должен подтвердить фактическое содержание этих сценариев.
3. Отдельно согласовать live exposure, стоимость и число вызовов. Получить по пять повторов исходного и исправленного конвейера на одинаковых входах; ошибки базы сохранять как failed runs. Старую базу с переполнением не заменять компактным поднабором и не включать `rules_only` вместо LLM-required extraction.
4. Выполнить неизменённый C03: `npm run eval:links -- --annotations <frozen-gold-with-prediction-paths> --out <report.json>`. Отдельно C03b: `node scripts/evaluate-mvp-extraction.mjs --gold <gold.json> --predictions <manifest.json> --out <report.json>`.
5. Сопоставить per-repeat/worst-repeat Precision/Recall/F1, row metrics, направление, paired evidence, negative/ambiguity gates, Jaccard, реальные ошибки/вызовы/tokens/cost и coverage. Отказ или неизвестный расход не записывать как ноль или успешный пустой граф.

## Оставшиеся ограничения

- Семантическая полнота, стабильность Gemma/DeepSeek и live исправление `POLZA_UNGROUNDED_OUTPUT` пока не подтверждены измерением.
- Число запросов на полном пятидокументном fixture сократилось с отказа прежнего bounded-плана (минимум 7908 новых задач при бюджете 28; отправка не начиналась) до 14 вызовов в offline candidate-run. Семантическая полнота нового candidate selector пока не подтверждена независимой gold-разметкой. При широком candidate set дополнительные verification/repair могут исчерпать Q1; такой run останется явно незавершённым, а не станет отрицательным результатом.
- Для вывода может потребоваться несколько разнесённых фрагментов. Дополнительный контекст ограничен и допускает один завершающий запрос задачи; невозможность вместить/завершить его остаётся явной ошибкой с checkpoint, а не отрицательным результатом.
- Семантически одинаковая связь с разными наборами evidence может остаться несколькими предложениями. Код намеренно не отождествляет разные отношения только по паре документов, типу и совпадающей сумме; это нуждается в bounded semantic reconciliation и измерении на gold.
- Нельзя гарантировать смысловую recall через границы длинных строк или таблиц только наличием всех срезов.
- Extraction сохраняет конечные checkpoints и диагностику ошибок. Сохранение на диск во время исполнения требует подключения `POLZA_ON_PROGRESS` потребителем; новая storage-инфраструктура вне scope не вводилась.
- Новые тесты читают committed Parser JSON, а не повторно распознают исходные PDF/XLSX/DOCX и не повторяют реальный Gateway E2E. Полные live E2E и человеческая разметка остаются следующими проверками.

Merge с интеграционной веткой и push не выполнялись.
