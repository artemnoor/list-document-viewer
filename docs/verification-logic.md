# Логика проверки

## Порядок допуска к сравнению

Для присвоения `matched` или `mismatch` движок должен разрешить actual и expected value, проверить семантический key и тип, период, currency/unit, VAT basis, comparison basis, полный calculation status, все использованные source references и их provenance. Все используемые источники должны быть явно `human_confirmed`; если источник связан через Linking, ссылка должна иметь `status=confirmed` и `verification_status=human_confirmed`, содержать соответствующее evidence и не иметь неразрешённой диагностики.

Неподтверждённая связь не подтверждает равенство. Необязательный `linking_result` не требуется для источника без `link_id`, но ссылка, заявленная в Reconciliation, должна разрешиться.

## Числовые правила

- Суммы приводятся к `Decimal` из исходной normalized amount; IEEE float не используется в вычислении разницы.
- `absolute = actual - expected`; относительная разница равна `(actual - expected) / abs(expected)`. При `expected = 0` она `null`.
- Валюты сравниваются только по точному коду. Автоматического FX пересчёта нет.
- Для `quantity` нужны одинаковые непустые единицы. Неизвестные конверсии не предполагаются.
- VAT `gross` и `net` несовместимы. `unknown` требует review.
- `actual` и `plan` — разные comparison basis; они не сравниваются как одно значение.
- Допуск отсутствует по умолчанию. Явная абсолютная tolerance применяется лишь при совпадении `absolute_unit` с валютой или измерительной единицей. Relative tolerance применяется лишь при ненулевом expected.
- `rounding_scale` и `rounding_mode` принимаются только если явно заданы. Сервис сохраняет raw difference даже когда округление её допускает.

## Содержательные значения

- `period` сравнивается по `start`/`end`; подтверждённое различие периодов классифицируется `wrong_period`.
- `string` сравнивается после Unicode NFC и схлопывания пробелов, без перевода и нечеткого совпадения.
- `date` сравнивается как нормализованная строка. Boolean сравнивается по типу и значению.
- Несовпадающий semantic key или несовместимый type/economic basis ведёт к `not_applicable`, а не к числовому mismatch.

## Статусы показателя

| Статус | Условие |
| --- | --- |
| `matched` | Значения эквивалентны по явным правилам; calculation полный, все references разрешены, evidence подтверждено |
| `mismatch` | Значения или период доказанно отличаются на полной и подтверждённой базе |
| `insufficient_data` | Не хватает значения, расчёт неполный, источник/provenance отсутствует или ссылка не разрешается |
| `needs_review` | Неоднозначная/неподтверждённая связь, конфликт, неизвестный basis или необходимость экспертного решения |
| `not_applicable` | Экономический смысл, тип, валюта, единицы или basis несовместимы |

Наличие численной разницы при неполной базе оставляет `difference` для диагностики, но не устанавливает категорию `amount_difference` и не создаёт `mismatch`.

Необязательный narrative provider Polza AI может предложить только гипотезу. При наличии `POLZA_AI_API_KEY` production app вызывает Gemma 4 26B A4B для показателей со статусом `mismatch`, `needs_review` или `insufficient_data`; для `matched` вызова нет. Модель получает обезличенный набор кодов и токенов evidence; суммы, IDs документов, подписи и текст источников не передаются. Ссылки из ответа должны разрешаться в исходный результат. Невалидная ссылка отклоняется, отказ provider добавляет диагностику. Никакой ответ LLM не влияет на значение, формулу, Decimal разницу или статус. За запросы отвечает тариф Polza AI.

## Общий статус запуска

Сводный статус консервативно выбирает худшее состояние: `needs_review`, затем `insufficient_data`, затем `mismatch`; `matched` возможен только если все показатели подтверждены. Если все показатели неприменимы, итоговый статус `not_applicable`. По этой причине отсутствие Reconciliation target для извлечённого индикатора создаёт результат `insufficient_data` и не скрывает его из сводки.
