# Phystech Trace

Модульная обработка комплектов КФЗ: Python Document Parser → Structured Extraction 1.2.0 → Document Linking 1.2.0 → Reconciliation Engine → Verification Engine. Сервисы запускаются отдельно; Gateway сохраняет проекты, этапы и промежуточные результаты. Единая точка входа — лендинг; рабочий кабинет построен на Vue 3 + TypeScript.

## Запуск

Из этого каталога выполните:

```powershell
docker compose up --build
```

Откройте http://localhost:8080. Первый build Parser image займёт больше времени из-за Docling и OCR-зависимостей. При первом OCR Parser может загрузить модели в постоянный volume.

Главная страница `/` — лендинг Phystech Trace, скопированный в `landing/`. Кнопки «Зарегистрироваться» и «Войти» открывают простые формы `/register` и `/logIn`; после отправки открывается кабинет `/app/` на том же адресе. Нужны только непустые почта и пароль; подтверждение почты и сложность пароля не проверяются. В кабинете — приветствие и сохранённые проекты. Первая карточка «+» открывает создание проекта по названию; выбор данных показан двумя открытыми карточками. «Конфиденциальные» использует `google/gemma-4-26b-a4b-it`, «Неконфиденциальные» — `deepseek/deepseek-v4.1-flash`. В обоих случаях содержимое обрабатывается через Polza AI; создание проекта или сохранение настроек разрешает передачу. Выбор применяется к извлечению, поиску пар, планированию расчёта и пояснениям сверки. При смене настроек результаты сбрасываются, оригиналы и распознанное содержимое сохраняются; проверку нужно запустить заново. Аккаунты и сессии сохраняются в PostgreSQL; выход доступен через аватар. Имя профиля редактируется через аватар и хранится в браузере отдельно для каждого аккаунта. Проекты остаются в общем рабочем пространстве. Внутри проекта дашборд ведёт по этапам: загрузка КФЗ и первичных файлов во вкладке «Документы», анализ, проверка связей и результаты сверки. Прогресс и ошибки отображаются по сохранённым состояниям сервисов. Ссылки `/app/?project=<id>` и `/app/?project=<id>&tab=verification` открывают конкретный проект и сверку; прежние ссылки от корня перенаправляются с сохранением параметров. Для разработки Vue-интерфейса `npm run dev` проксирует `/api` на локальный Gateway, порт 8084.

Остановка: `docker compose down`. Compose volumes сохраняют PostgreSQL, Redis, загруженные оригиналы и OCR-модели. Для удаления данных вместе с контейнерами: `docker compose down -v`.

## Web-интерфейс

`landing/` содержит публичные страницы и ресурсы, `frontend/` — Vue-кабинет и общую сборку, `gateway/` — общий API. Обе части обслуживает один nginx; дополнительный сервер лендинга не нужен. Структура, маршруты и команды разработки: [`docs/web-integration.md`](docs/web-integration.md).

## Конфигурация и приватность

Compose запускается без `.env`. Чтобы задать свои секреты, скопируйте `.env.example` в `.env`. `POLZA_API_KEY` необязателен: без него локальный Parser и rules-only Extraction доступны, а Linking сообщает диагностируемую ошибку отсутствующего ключа. На Windows Compose также автоматически читает уже заданный `POLZA_AI_API_KEY` из переменных среды.

В текущем прототипе оба класса данных используют внешнюю Polza AI с разрешения пользователя. Классификация выбирает модель, но не обеспечивает локальную обработку. Это временное допущение прототипа: для выполнения ограничения кейса конфиденциальный режим необходимо перевести на локальную модель. Gateway и сервисы проверяют разрешение на внешнюю обработку; ключ хранится на сервере. Проверка распознавания через AI также использует Polza AI.

Форматы и лимиты соответствуют существующему Parser: PDF, изображения, DOCX, XLSX/XLSM, CSV, TXT и другие заявленные форматы; ограничение загрузки — 25 MiB.

## Проверки

```powershell
python -m unittest discover -s tests/contracts -v
python tests/e2e/run_e2e.py --base-url http://localhost:8084
python tests/e2e/run_e2e.py --compact-linking --base-url http://localhost:8084
python tests/e2e/review_decisions.py --project-id <project-id>
python tests/e2e/verify_saved_project.py --project-id <project-id>
```

E2E использует HTTP API настоящих сервисов и синтетические fixtures. Компактный профиль проверяет реальные вызовы Polza, ожидаемые отношения и evidence PDF/XLSX/DOCX. `review_decisions.py` отдельно подтверждает одну связь и отклоняет другую через Gateway API, проверяя сохранность evidence и решений. Стандартный профиль дополнительно включает fixtures изображения и сложного сканированного PDF, дубликат и более крупный пакет; его Linker результат записывается отдельно и может быть ограничен контекстом/форматом ответа модели. Mock LLM тесты не являются проверкой Polza.

Последний компактный E2E прошёл через Parser, Extraction и Linking с реальной Polza-моделью на синтетических данных; широкий комплект из пяти документов прошёл Parser и Extraction, но Linking вернул диагностируемую ошибку контекста/формата ответа. Точные результаты и ограничения записаны в [`docs/integration-report.md`](docs/integration-report.md), [`tests/e2e/results/latest-run.json`](tests/e2e/results/latest-run.json) и [`tests/e2e/results/full-set-live-attempt.json`](tests/e2e/results/full-set-live-attempt.json).

См. [`docs/architecture.md`](docs/architecture.md), [`docs/data-flow.md`](docs/data-flow.md), [`docs/contracts.md`](docs/contracts.md) и [`docs/integration-report.md`](docs/integration-report.md).

Во вкладке «Документы» показаны индивидуальные состояния файлов: обработан (текст распознан и данные извлечены), в обработке, ожидает или ошибка. Счётчики и фильтры обновляются автоматически. Нажатие на файл открывает распознанную Markdown-версию с оформлением и таблицами; доступны исходный Markdown и скачивание `.md`. Найденные значения находятся на отдельной вкладке. Распознанный текст доступен и при незавершённом или неудачном извлечении данных. Просмотр Markdown изолирован от приложения и не выполняет скрипты.


## Типовые сценарии и проверка кейса

1. Совпадающие показатели: загрузите КФЗ с итогом 120 000 руб. и два акта одного договора и периода на 70 000 и 50 000 руб. Ожидаемый расчёт — 120 000 руб., расхождение — 0. Статус «совпадает» допустим при достаточных и проверенных источниках; неоднозначные связи требуют проверки.
2. Расхождение и недостаток данных: для КФЗ 120 000 руб. валидные документы дают 110 000 руб., а подтверждение трудоёмкости отсутствует. Ожидается расхождение 10 000 руб. по сумме и отдельный непроверенный показатель трудоёмкости. Дубли исключаются из повторного учёта, другой договор и другой период сохраняются в диагностике.

Произвольные показатели КФЗ извлекаются как `indicators` с точным исходным значением и provenance; в расчёт передаются денежные и числовые показатели. Служебный счётчик распознанных строк не является показателем отчёта. Отсутствие подтверждения должно давать недостаточность данных, а не нулевое ожидаемое значение.

Набор кейса 19 включает эталон `!Правильные_ответы_и_разбор.xlsx` и README: они предназначены только для оценки и не должны загружаться как первичные документы. Ожидаемый результат по эталону: завышение статьи 0800 и общего итога на 12 500 руб., исключение дубля, документа вне периода и другого договора. Это ожидаемый результат теста, а не заявление о прохождении полного комплекта.

Дальнейшее развитие: локальные модели для конфиденциального режима, проверка на независимых размеченных сканах, повышение устойчивости извлечения широких таблиц и связывания больших комплектов. Полный комплект кейса 19 проверен локальным аудитом по независимому эталону; результаты и границы приведены в docs/case-compliance.md.


## Автоматическая сверка статей затрат

В настройках проекта задайте строку/этап и период первички. Режим «Автоматически» выполняет локальную сверку явно определяемых статей оплаты труда, страховых взносов, общепроизводственных и общехозяйственных затрат: проверяет договор, период, дубли и полноту месячных ведомостей, выбирает итог документа без повторного сложения его компонентов и сравнивает Decimal-суммы. Суммы и имена файлов эталона не зашиты в правила. Неподтверждённые подпоказатели и неразрешённые источники сохраняются отдельно.

Для набора кейса: строка `3 этап 2026`, период `2026-01-01`—`2026-05-31`. Результат: три статьи совпадают, 0800 и общий итог завышены на 12 500 руб.; это одно завышение, отражённое в двух строках. См. [проверку соответствия](docs/case-compliance.md).

В `local-cost-audit/1.1` период из настроек имеет приоритет; без него используется подтверждённый период самого отчёта. Дата создания отчёта период не заменяет. Если период неизвестен или противоречив, результат остаётся непроверенным. Для оплаты труда и взносов первичка должна покрывать весь период, а не только содержать документ каждого месяца. Копии одной операции сопоставляются по номеру, договору, периоду, статье и поставщику независимо от OCR-текста; конфликт сумм или валют требует проверки. Общий итог рассчитывается по статьям отчёта и наследует недостаточность данных основных составляющих. Неподтверждённая ненулевая статья блокирует уверенный статус итога; подколонки поддержанного итога статьи не складываются повторно. Старые сохранённые расчёты обновляются кнопкой повторной сверки.

Во вкладке результатов доступны формулы, исходные файлы, точные значения и provenance, учёт исключённых документов, скачивание заключения Markdown и JSON. Автоматический расчёт сохраняется в `financial_audit`; этапы имеют `mode=local_cost_audit`. Расширенный поиск связей выбирается отдельно в настройках (`verification_scope.calculation_mode=semantic`) и использует существующие Linking/Reconciliation/Verification API. Успех локальной сверки не означает успешного выполнения семантического режима.

API настроек поддерживает `verification_scope`: `report_row`, `period_start`, `period_end`, `calculation_mode` (`auto` по умолчанию). При смене области расчёт и заключение сбрасываются. API `POST /api/projects/{id}/documents/{document_id}/reextract` позволяет заново извлечь один файл либо набор `document_ids`, сохранив OCR; необязательный `mode=rules_only` выполняет локальный разбор. Изменение извлечения сбрасывает зависимые результаты.

Для большого семантического комплекта Compose разрешает до 256 вызовов и 30 минут (`LLM_MAX_CALLS_PER_RUN`, `LLM_MAX_RUN_MS`); это предел, а не обещание завершения. Локальная сверка не расходует эти вызовы. Расчёт независимых целей Reconciliation может использовать до четырёх потоков (`TARGET_WORKERS`).

Заключение открывается кнопкой «Заключение · PDF». `GET /api/projects/{id}/report.pdf` формирует PDF с кириллицей, суммами, ссылками на оригиналы и актуальным решением по версии отчёта. Просмотр и скачивание используют один PDF; браузерный кеш отключён. Шрифты DejaVu и их лицензия поставляются в `gateway/assets/fonts`. Для установки зависимостей серверных тестов: `python -m pip install -r tests/requirements.txt`, затем `python -m pytest tests -q`.

Подписи размещения моделей в демонстрационном интерфейсе согласованы как макет: «Gemma 26B · локально» и «DeepSeek · сторонний API». Они не меняют фактическую маршрутизацию прототипа. Реальный перенос Gemma на локальный сервер ещё предстоит; сам по себе новый текст интерфейса локальный инференс не включает.
